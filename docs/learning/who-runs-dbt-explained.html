🧚 Who Runs dbt? — Scheduler vs Tool, Explained Like You're 5

You know Airflow: it's a daemon that lives in Docker and breathes 24/7. So where does dbt live? Spoiler: dbt has no daemon. It's a hammer, not a clock.

The 5-year-old story

⏰Airflow is an alarm clock. The clock never sleeps. It sits in your house (a Docker container), ticking every second, and when the alarm rings it wakes someone up to do the chore. The clock + the sleeping worker both live with you, eating electricity all day, even when nothing is happening.
🔨dbt is a hammer in a toolbox. It doesn't tick. It doesn't breathe. It just waits, quietly, as a program on a shelf. Nothing happens until somebody picks it up and swings it — dbt build. The moment the job is done, the hammer goes back on the shelf. No house, no electricity, no container needed between jobs.
🤖So who swings the hammer every day at 00:00 UTC? In this repo: GitHub Actions. GitHub has a giant room full of computers. At midnight UTC, GitHub's own alarm clock rings, GitHub lends you one computer for ~2 minutes, that computer installs dbt (picks the hammer out of the box), runs dbt build, and then the computer is returned to the shelf. You never saw the machine. You never maintained it. That's why nothing in your repo needs Docker.

dbt vs Airflow — same job, different philosophy

🌀 Airflow (what you know)

  • Always-on daemon — scheduler + webserver + workers run 24/7
  • Lives in your Docker containers / your VM / your k8s cluster
  • You patch it, upgrade it, restart it, pay for it while it idles
  • Schedule is inside the product (schedule="@daily")
  • Great when: many pipelines, complex dependencies, backfills, sensors, cross-team orchestration

⚡ GitHub Actions cron (what this repo uses)

  • No daemon at all — ephemeral runner born for one job, dies after
  • Lives on GitHub's computers; you rent it per-minute (free for public repos)
  • Zero maintenance — no containers to babysit, ever
  • Schedule is outside the tool, in YAML: cron: '0 0 * * *'
  • Great when: 1 repo, a handful of pipelines, schedules are simple

So… where does dbt actually "live"? (3 honest answers)

dbt is just a Python package (pip install dbt-duckdb). It lives wherever someone installs it:

1. Your laptopthis repo's .venv.venv/Scripts/dbt.exe
2. A CI runner (2-min life)born at 00:00 UTC, deleted at 00:02GitHub's ubuntu-latest VM
3. Inside Airflow (if you want)the hammer hangs on Airflow's wallCosmosPlugin / BashOperator
💡 Key mental model: dbt has no "dbt server", "dbt scheduler", or "dbt container". Compare: Airflow is the clock + the worker. dbt is only the worker. Every dbt deployment on Earth answers "who triggers it?" with something else: Airflow, Dagster, Prefect, cron on a VM… or GitHub Actions.

"But Airflow already does this in my other repo — which is right?"

Both. They're different points on a cost/complexity curve:

Maintenance burden0 — GitHub patches the runnersyou: image upgrades, restarts, monitoring

⚠️ When to graduate to Airflow: the day this project has 20+ pipelines, cross-pipeline dependencies ("refresh FX before pricing model"), retry logic spanning days, or consumers waiting on SLAs — that's when a real clock like Airflow earns its Docker container. For one repo + one daily refresh, GitHub's clock is strictly simpler.

TL;DR

dbt never needs a machine of its own — it's a program that runs, finishes, and stops, like any python script.py. What your Airflow brain calls "the scheduler" lives outside dbt. In this repo, GitHub Actions is the scheduler: its cron rings at 00:00 UTC, lends you a throwaway computer for two minutes, that computer installs dbt + Python + Node, does the whole pipeline, deploys the dashboard, and dissolves into nothing. No Docker. No daemon. No machine to babysit. The "system" that runs dbt is just a hammer + someone else's alarm clock. 🔨⏰
