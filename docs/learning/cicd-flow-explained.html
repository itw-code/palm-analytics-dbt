Guardrail 1 — no deploy races with manual pushes

Two runs of pages.yml touching GitHub Pages at the same time would corrupt the deploy. The fix is a concurrency group:

concurrency:
  group: pages
  cancel-in-progress: false   # ← the important line

❌ Before (cancel-in-progress: true)

  • You push at 00:00:01 while the cron runs
  • Cron gets killed mid-deploy
  • Pages can be left half-updated

✅ After (false)

  • Manual run finishes first
  • Cron queues, runs immediately after
  • Worst case: dashboard is a few minutes "late"

dbt.yml uses group: dbt-ci-${{ '{' }}{{ 'github.ref' }}{{ '}' }} instead — so main and PR branches never block each other, but the same branch can't run twice in parallel.

Guardrail 2 — ingestion failures are never silent

The tricky part of "always-reproducible CI" is that synthetic fallback can mask a dead API with a green ✅. The design response: graceful by default, loud by design.

API upmode: "live"
rows counted
API down → retry 3×2s/4s/6s backoff
still down → syntheticmanifest records mode+error
--require-liveor INGEST_REQUIRE_LIVE=1
→ exit 1, run fails
# workflow logic — scheduled runs can opt into strict mode via a repo variable
if [ "${{ github.event_name }}" = "schedule" ] && [ "${INGEST_REQUIRE_LIVE:-0}" = "1" ]; then
  python ingestion/load_raw.py --require-live
else
  python ingestion/load_raw.py          # fallback allowed, but LOUD
fi
💡 Default is graceful on purpose: a 5-minute Frankfurter hiccup shouldn't leave the dashboard frozen for 24h until the next cron. The manifest + summary warning means you'll know — and can flip the variable to fail-fast once you trust the pipeline.

Guardrail 3 — freshness that fails the right way

The old workflow had continue-on-error: true on freshness — i.e. it could never fail. Now:

dbt source freshness --output target/freshness.json || true
# then parse:  status "warn"  → ::warning:: annotation, run stays green
#             status "error" → ::error:: + exit 1 → run goes red
SourcewarnerrorRationale
raw_weather / raw_fx_rate3 days90 daysmissed daily cron visible next morning; error threshold wide enough that the deterministic CI fixture doesn't false-alarm
raw_commodity_price35 days95 daysmonthly cadence — warn if a month's price didn't arrive

Guardrail 4 — you hear about failures

  • Workflow Summary — every run writes the ingestion manifest + freshness table to the run's Summary tab (visible without opening logs).
  • Auto-Issue on scheduled failure — opens Scheduled dbt build failed — YYYY-MM-DD; if one is already open, it comments instead of spamming duplicates. Needs permissions: issues: write.
  • Artifacts on failure — run_results.json, freshness.json, ingestion_manifest.json, logs/dbt.log (14-day retention).

Speed: caches & timeouts

# actions/setup-python@v5
cache: pip                    # requirements.txt → cached wheels

# actions/setup-node@v4
cache: npm
cache-dependency-path: dashboard/package-lock.json

timeout-minutes: 25           # hung runner can't burn your CI minutes

Also note npm ci (not npm install) — uses the lockfile exactly, faster and reproducible.

Every midnight UTC → same thing, plus: fresh APIs, freshness gates, manifest in Summary, auto-issue if red.
