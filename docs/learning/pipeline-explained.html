0.The big picture — ELT, not ETL

This project follows the Modern Data Stack pattern: Extract & Load (Python dumps raw data into the warehouse untouched), then Transform (dbt does all cleaning/business logic inside DuckDB with SQL). There is no separate "transform in Python" step — SQL is the transformation language, version-controlled and testable.

💡 Why ELT? Raw data stays queryable for debugging ("what did the API actually return?"), and dbt gives you lineage, tests, and docs for free — things a Python script can't provide.

Key ideas in the script:

# 1) RETRY with backoff — transient API blips shouldn't fail the whole pipeline
def fetch_with_retry(fn, *, retries=3, backoff=2.0, label=""):
    for attempt in range(1, retries + 1):
        try:
            return fn()
        except Exception as e:
            ...
            time.sleep(backoff * attempt)  # 2s, 4s, 6s…

# 2) DETERMINISTIC FALLBACK — if offline, generate synthetic-but-stable data
#    so CI is always reproducible. NEVER silent: a manifest records provenance.
provenance["sources"]["fx"] = {"mode": "synthetic", "error": str(e)}
# → ingestion_manifest.json → shown in the GitHub Actions run Summary

# 3) LOAD — plain CREATE TABLE + executemany into DuckDB (no cleaning here!)
con = duckdb.connect("palm.duckdb")
con.execute("CREATE OR REPLACE TABLE raw_fx_rate (rate_date DATE, usd_idr DOUBLE)")
con.executemany("INSERT INTO raw_fx_rate VALUES (?,?)", rows)
⚠️ Production lesson: the fallback is graceful but loud. In CI a green build with "mode": "synthetic" would be a silent data-quality failure — the manifest + ::warning:: annotations exist precisely so you can't miss it. Pass --require-live to make degradation fail the run instead.

2.The Warehouse — why DuckDB?

DuckDB is "SQLite for analytics": a single file (palm.duckdb), zero servers, columnar + vectorized execution. Perfect for a laptop-sized warehouse, and it scales to MotherDuck (cloud) by changing one profile line.

# profiles.yml — the only config dbt needs to talk to the warehouse
palm_analytics:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: palm.duckdb
      threads: 4          # parallel model builds

3.Transform — dbt layers (stg → int → marts)

dbt models are just SQL files with a ref() graph. This repo uses the standard 3-layer architecture:

staging (views) — 1:1 with sources

  • stg_weather — rename + cast, nothing else
  • stg_fx_rate, stg_holidays, stg_commodity_price
  • Goal: a clean, typed contract per source

intermediate (views) — reusable logic

  • int_calendar — date spine
  • int_fx_daily — ASOF forward-fill
  • int_commodity_daily — monthly→daily fill
  • int_daily_agronomy_signals — business rules

marts (tables) — the star schema

  • dim_date, dim_region
  • fct_estate_operations_daily (incremental)
  • fct_commodity_price_daily (contract)
  • What dashboards consume

The most interesting SQL trick — ASOF joins for forward-filling sparse series (FX exists only on business days, prices only monthly) onto a daily spine:

-- int_fx_daily.sql: for each calendar day, take the LATEST rate on-or-before it
select
    c.date_day,
    f.usd_idr
from {{ ref('int_calendar') }} c
asof left join {{ ref('stg_fx_rate') }} f
    on c.date_day >= f.rate_date
💡 Business rules live in intermediate: "fertilize when 5–25 mm rain and soil moisture < 0.35", "spray when wind < 12 km/h and rain < 5 mm". Encoded once as booleans (is_fertilize_favorable), reused by marts and the dashboard.

4.Incremental models — don't rebuild everything

fct_estate_operations_daily is incremental: on the first run it builds fully; afterwards it only processes new dates:

{{ config(materialized='incremental',
         unique_key='operations_key',
         incremental_strategy='delete+insert',   # DuckDB-friendly
         on_schema_change='sync_all_columns') }}

...
{% if is_incremental() %}
where signals.weather_date > (select max(operation_date) from {{ this }})
{% endif %}

delete+insert deletes rows matching unique_key then inserts fresh ones — idempotent re-runs, late-arriving days get corrected, and the scan is pruned to only new dates.

6.Serve — Evidence.dev → static HTML → GitHub Pages

Evidence pages are Markdown + SQL. Each SQL block runs against DuckDB; Svelte components render charts:

```sql headline
select max(operation_date) as as_of, max(cpo_idr_per_tonne) as cpo_idr
from palm.operations_daily
```

<BigValue data={headline} value=cpo_idr title="Palm price (IDR/tonne)"/>

evidence build compiles everything into a static site (dashboard/build/) — no BI server to run, hosting is free on GitHub Pages.

7.Automate — the daily 00:00 UTC refresh

Two GitHub Actions workflows make it hands-off:

WorkflowTriggersDoes
dbt.ymlpush / PR / daily croningest → dbt build → freshness → docs
pages.ymlpush to main / daily cron / manualfull E2E → deploy static site
on:
  push: { branches: [main] }
  pull_request:
  schedule:
    - cron: '0 0 * * *'   # daily 00:00 UTC

concurrency:
  group: pages
  cancel-in-progress: false  # cron QUEUES behind your manual push — no kill

Observability built in: the run Summary shows the ingestion manifest (live vs synthetic per source) + freshness status; a scheduled failure auto-opens a GitHub Issue; diagnostics are uploaded as artifacts.

TermPlain meaning
